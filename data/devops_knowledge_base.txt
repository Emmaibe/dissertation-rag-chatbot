=== DOCUMENT 1: Introduction to DevSecOps ===

DevSecOps is a software development approach that integrates security practices into the DevOps pipeline. 
The term stands for Development, Security, and Operations. Unlike traditional models where security is 
applied at the end of the development cycle, DevSecOps embeds security controls at every stage of the 
software delivery lifecycle.

Key principles of DevSecOps include:
- Shift-left security: identifying and resolving security issues earlier in the development process
- Continuous security testing: automated security scans on every code commit
- Infrastructure as Code (IaC) security: scanning Terraform, Ansible and Kubernetes manifests
- Developer-owned security: developers take responsibility for secure coding practices

Common DevSecOps tools include SonarQube for static application security testing (SAST), Trivy for 
container image scanning, OWASP Dependency Check for software composition analysis, and HashiCorp Vault 
for secrets management.

=== DOCUMENT 2: Retrieval-Augmented Generation (RAG) ===

Retrieval-Augmented Generation (RAG) is a technique that enhances Large Language Model (LLM) responses 
by retrieving relevant context from an external knowledge base before generating an answer. RAG was 
introduced by Lewis et al. (2020) and has since become a foundational approach in production AI systems.

The RAG pipeline consists of two main phases:
1. Indexing phase: Documents are chunked, embedded using an embedding model, and stored in a vector store.
2. Retrieval and generation phase: A user query is embedded, similar chunks are retrieved from the vector 
   store using cosine similarity or other distance metrics, and the retrieved context is passed to an LLM 
   to generate a grounded response.

RAG addresses the hallucination problem in LLMs by grounding responses in retrieved source documents. 
This makes it particularly suitable for enterprise knowledge management, customer support systems, and 
domain-specific question answering.

Key RAG evaluation metrics include:
- Context Precision: measures the proportion of retrieved chunks that are genuinely relevant to the query
- Faithfulness: measures the degree to which the generated answer is grounded in the retrieved context
- Answer Relevance: measures how well the generated answer addresses the user's original question

=== DOCUMENT 3: LLMOps ===

LLMOps (Large Language Model Operations) extends the principles of MLOps to address the specific 
operational challenges of deploying and maintaining LLM-based applications in production. LLMOps 
encompasses prompt management, model versioning, output evaluation, cost monitoring, and governance.

Key LLMOps practices include:
- Prompt versioning: tracking changes to system prompts and evaluating their impact on output quality
- Continuous evaluation: automatically evaluating LLM outputs using frameworks such as RAGAS
- Cost monitoring: tracking token usage and API costs across different model configurations
- Observability: capturing latency, error rates and model-specific metrics in dashboards
- Guardrails: implementing input/output filters to prevent harmful or off-topic responses

LLMOps differs from traditional MLOps in several ways. LLMs are rarely retrained from scratch; instead, 
they are adapted through prompt engineering, fine-tuning or retrieval augmentation. Evaluation is also 
more complex because LLM outputs are often free-form text that cannot be easily compared using 
traditional classification or regression metrics.

=== DOCUMENT 4: Kubernetes and K3s ===

Kubernetes is an open-source container orchestration platform that automates the deployment, scaling, 
and management of containerised applications. It was originally developed by Google and released as 
open source in 2014.

K3s is a lightweight Kubernetes distribution developed by Rancher Labs (now part of SUSE). It is 
designed for resource-constrained environments such as edge computing, IoT devices, and cost-optimised 
cloud deployments. K3s packages the full Kubernetes API into a single binary of less than 70MB, 
significantly reducing the operational overhead associated with a standard Kubernetes installation.

Key advantages of K3s for this project:
- Single binary installation: K3s can be installed on an AWS EC2 instance with a single command
- Low resource footprint: suitable for t3.large EC2 instances with 8GB RAM
- Full Kubernetes API compatibility: workloads designed for K3s can be migrated to full Kubernetes
- Built-in containerd runtime: eliminates the need to separately install Docker as a container runtime
- Simplified certificate management: K3s automatically manages TLS certificates for cluster components

=== DOCUMENT 5: CI/CD with Jenkins ===

Continuous Integration and Continuous Deployment (CI/CD) is a software engineering practice that 
automates the building, testing, and deployment of applications. Jenkins is one of the most widely 
used open-source CI/CD servers, with a large ecosystem of plugins and strong support for pipeline-as-code.

A typical Jenkins pipeline for a RAG chatbot includes the following stages:
1. Source checkout: Jenkins pulls the latest code from the GitHub repository
2. Dependency installation: Python dependencies are installed in a virtual environment
3. Unit testing: pytest runs the test suite and generates a coverage report
4. Static analysis: SonarQube Scanner analyses the codebase for code quality and security issues
5. Container build: Docker builds the application image and tags it with the commit SHA
6. Container scan: Trivy scans the Docker image for known vulnerabilities
7. Deployment: Ansible applies Kubernetes manifests to the K3s cluster on AWS EC2

Jenkins pipelines are defined as Jenkinsfile in the root of the repository, enabling pipeline-as-code 
and version control of the CI/CD configuration.

=== DOCUMENT 6: Prometheus and Grafana Observability ===

Prometheus is an open-source monitoring and alerting toolkit originally developed at SoundCloud. 
It uses a pull-based model to scrape metrics from instrumented applications and infrastructure components. 
Metrics are stored in a time-series database and can be queried using PromQL (Prometheus Query Language).

Grafana is an open-source visualisation platform that integrates with Prometheus and other data sources 
to create interactive dashboards. In the context of this project, Grafana dashboards will provide 
visibility into:
- RAG pipeline latency: end-to-end response time from query submission to answer delivery
- Retrieval metrics: number of chunks retrieved, retrieval latency, and embedding generation time
- LLM API metrics: token usage, API response time, and error rates
- Infrastructure metrics: CPU usage, memory consumption, and pod restart counts on K3s
- CI/CD metrics: pipeline execution time, build success rate, and deployment frequency

Prometheus and Grafana are deployed as Kubernetes workloads within the K3s cluster, alongside the 
RAG chatbot application.

=== DOCUMENT 7: Ansible for Deployment Automation ===

Ansible is an open-source IT automation tool developed by Red Hat. It uses a declarative, 
agent-less architecture where automation tasks are defined in YAML files called playbooks. 
Ansible connects to remote hosts over SSH and executes tasks in sequence, making it well-suited 
for repeatable infrastructure provisioning and application deployment.

In this project, Ansible is used to automate the deployment of the RAG chatbot and its supporting 
infrastructure to an AWS EC2 instance running K3s. Key Ansible playbooks include:
- provision.yml: installs K3s, Docker and system dependencies on the EC2 instance
- deploy.yml: applies Kubernetes manifests for the RAG chatbot, Prometheus and Grafana
- rollback.yml: reverts to the previous deployment if a health check fails

Ansible's idempotent execution model ensures that running the same playbook multiple times produces 
the same result, which is essential for deployment repeatability — one of the key evaluation metrics 
in this project.
